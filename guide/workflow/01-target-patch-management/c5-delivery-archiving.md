# UC01-C5: Delivery, Delta Spec Writing, Sync & Archiving

## 1. Overview & Operational Scope

Stage C5 (Delivery, Delta Spec Writing, Sync & Archiving) represents the final delivery stage of the Target Patch Management workflow (`UC01`). In this stage, per-PR delta specifications are authored via `spec-delta-writer`, final delivery authorization is granted via Human-in-the-Loop (HITL) Gate 2, spec changes are synchronized to main specifications via `/opsx-sync`, and completed change proposals are archived via `/opsx-archive`.

---

## 2. Key Agents & MCP Tooling

| Role / Tool | Identity / Command | Operational Purpose |
|:---|:---|:---|
| Specialist Agent | `spec-delta-writer` | Authors canonical per-PR delta specs describing precise behavior changes introduced by the patch. |
| Command | `/opsx-sync` | Synchronizes delta specifications into main specification files. |
| Command | `/opsx-archive` | Archives completed change proposal packages. |
| Audit Agent | `spec-freshness-checker` | Verifies spec hash commitments and detects stale specification references. |
| Maintenance Agent | `doc-updater` | Updates master navigation indexes, codemaps, and README documentation. |

---

## 3. Mandatory Per-PR Delta Spec Writing (`spec-delta-writer`)

To guarantee zero spec drift and preserve specification integrity across pull requests:

1. **Per-PR Delta Writing Rule**: Every delivered patch file staged in `harness/patches/` **MUST** be accompanied by a per-PR delta spec generated by `spec-delta-writer`.
2. **Delta Spec Location**: Delta specs are stored within the change folder or under `openspec/changes/<change-id>/specs/`.
3. **Structure of Delta Spec**:
   - **ADDED Clauses**: New requirements or scenarios introduced.
   - **MODIFIED Clauses**: Altered existing behaviors with explicit before/after diffs.
   - **REMOVED Clauses**: Deprecated or deleted behaviors.

---

## 4. Mandatory Human-in-the-Loop (HITL) Gate 2 Approval

Before applying patches, merging pull requests, or syncing delta specs into production baselines, **HITL Gate 2** must be passed.

### Gate 2 Criteria:
1. **Staged Patch Inspection**: Human developer reviews the final unified diff file in `harness/patches/`.
2. **Review Verification Sign-Off**: Verification report from Stage C4 (4-Step Spec Check & Security Audit) passes with zero unresolved blocking defects.
3. **Delta Spec Validation**: Developer confirms per-PR delta spec generated by `spec-delta-writer` accurately reflects patch behavior.
4. **Final Approval**: Developer issues explicit approval to apply patch or merge PR.

---

## 5. Sync & Archiving Protocol

### Step 5.1: Synchronize Specs (`/opsx-sync`)
Execute `/opsx-sync` to merge the per-PR delta specifications into main specifications:

```bash
# Command invocation to sync delta specs to main baseline
/opsx-sync change="refactor-target-navigation"
```

### Step 5.2: Spec Freshness Audit (`spec-freshness-checker`)
Deploy `spec-freshness-checker` to compute and commit SHA-256 spec content hashes:
- Validate spec hash commitments against codebase state.
- Ensure no undocumented modifications exist in main specs.

### Step 5.3: Documentation Update (`doc-updater`)
Deploy `doc-updater` to refresh project documentation, API references, and codemaps affected by the change.

### Step 5.4: Archive Change Proposal (`/opsx-archive`)
Execute `/opsx-archive` to finalize and archive the change folder:

```bash
# Archive completed change proposal
/opsx-archive change="refactor-target-navigation"
```

---

## 6. Deliverables & Completion Verification

Upon completing Stage C5:
1. Staged patch file (`harness/patches/*.patch`) delivered and approved at HITL Gate 2.
2. Per-PR delta spec written by `spec-delta-writer` and merged into main specs via `/opsx-sync`.
3. Spec freshness hash verified by `spec-freshness-checker`.
4. Change proposal archived cleanly via `/opsx-archive`.

The Target Patch Management (`UC01`) workflow execution cycle is now **COMPLETE**.
